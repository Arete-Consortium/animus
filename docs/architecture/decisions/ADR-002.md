# ADR-002: Store typed knowledge edges in Core durable storage

Status: Accepted for pilot; production rollout pending
Date: 2026-11-21

## Context

Animus already has a Core memory layer, a bitemporal durable object registry,
an immutable event ledger, workspace/security scope checks, candidate
validation, and export/restore. It also has a JSON entity graph and an
analysis-only Dossier graph. Kernel contains a drifting duplicate memory
implementation. Forgehand now has a bounded context-consumption seam.

A separate graph database would duplicate persistence and add operational
infrastructure without evidence of need.

## Decision

Add typed knowledge-edge records beside the Core durable registry. Keep edge
records versioned, evidence-bearing, scoped, ledgered, and exportable. Expose
bounded immediate-neighbor queries through the durable store.

Use the controlled predicate set in the knowledge_edge contract. Proposed
records remain unverified until the existing candidate and approval lifecycle
authorizes promotion.

Core owns shared knowledge. Forgehand consumes bounded context and submits
proposals. Quorum owns intent and coordination. Governor owns authorization
and policy. The knowledge graph provides information, not permission.

## Alternatives

- Extend free-form Memory metadata: rejected as the sole storage model because
  typed edge queries and integrity constraints would be implicit.
- Dedicated graph database/service: rejected for this pilot because it adds
  deployment, backup, authorization, and migration cost without demonstrated
  query or scale requirements.
- Make Kernel, Memboot, or Dossier the authority: rejected because each has a
  narrower scope or an incompatible persistence/trust model.

## Pilot scope

The pilot adds the knowledge_edges table, the typed edge contract, atomic
create/supersede plus ledger/outbox events, bounded neighbor queries, and
SQLite tests. It does not migrate production databases, bulk import projects,
integrate Quorum writes, or deploy to Stheno.

## Migration and rollback

Migration 003 is explicit and reversible only when the edge table is empty.
Existing databases must be backed up and upgraded through Alembic. The durable
store continues to fail closed on schema mismatch. Rollback after populated
edges requires an evidence export and reviewed recovery; the downgrade refuses
to drop a populated table.

## Consequences

Positive: reuses existing durability, provenance, scope, history, and
recovery contracts; preserves ownership boundaries; enables Forgehand pilot
retrieval.

Accepted costs: one new table and migration, typed query API maintenance,
Core/Kernel contract reconciliation, and later evaluation work.

## Acceptance gate

Before production activation, demonstrate migration rehearsal, restart
recovery, export/restore, scope isolation, candidate approval, Forgehand
retrieval bounds, and historical-task evaluation.
